# Visa Assignment API

A Go REST API for member management and points-based rewards. The service uses Gin for HTTP routing, SQL Server for persistence, zerolog for structured logging, and Swagger UI for interactive API documentation.

## Features

- Create and retrieve members.
- View a member's current points balance and reward history.
- Record points credits and redemptions.
- Prevent redemptions that exceed the member's available balance.
- Attach a unique request ID to each HTTP request and include it in the response header and structured logs.
- Browse and try the endpoints in Swagger UI.

## Requirements

- Go version specified by `go.mod` (currently Go 1.27.3).
- A reachable Microsoft SQL Server instance.
- The database schema described under [Database](#database).

The repository vendors its Go dependencies. From the repository root, build and test with:

```powershell
go test ./...
go build .
```

## Configuration

At startup, the application reads `resources/application.yml` relative to the current working directory. Run the service from the repository root.

The configuration loader expects the database key `connectionString` and a top-level `port`. For example:

```yaml
database:
  connectionString: "server=localhost;port=1433;database=vivek_db;trusted_connection=yes;encrypt=disable;trustservercertificate=true"
port: 8080
```

Update the connection string for your SQL Server and authentication method. The YAML currently checked in uses `connection_string` and places `port` under `database`; those keys do not match the configuration struct and should be changed to the format above.

If `port` is omitted or set to `0`, the HTTP server listens on port `8080`.

## Database

The repository queries the `vivek_db.dbo.members` and `vivek_db.dbo.rewards` tables. Create the database and tables before starting the application. The code expects these columns:

| Table | Columns used |
| --- | --- |
| `members` | `member_id`, `name`, `email`, `created_at` |
| `rewards` | `reward_id`, `member_id`, `point_type_id`, `points`, `description`, `event_date` |

`member_id` and `reward_id` should be generated by the database when a row is inserted. The rewards table should reference a valid member. Redemption operations use SQL Server row-level update locks and transactions to check the balance and insert atomically.

## Run

From the repository root:

```powershell
go run .
```

The service connects to SQL Server before starting the HTTP listener. Startup and database connection failures are logged as structured zerolog events.

## API documentation

With the service running:

- Swagger UI: <http://localhost:8080/swagger>
- OpenAPI specification: <http://localhost:8080/swagger/openapi.yaml>

Swagger UI assets are loaded from jsDelivr, so the UI requires network access to that CDN. The OpenAPI file itself is served by the application.

## Endpoints

All application endpoints are unauthenticated. The `/v1` prefix applies to member and reward operations.

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/health` | Health check |
| `POST` | `/v1/members` | Create a member |
| `GET` | `/v1/members/{memberId}` | Get a member and current points balance |
| `GET` | `/v1/members/{memberId}/rewards` | List a member's reward entries |
| `POST` | `/v1/rewards` | Add points or redeem points |

### Health check

```powershell
curl.exe http://localhost:8080/health
```

Example response:

```json
{"status":"UP"}
```

### Create a member

```powershell
curl.exe -X POST http://localhost:8080/v1/members `
  -H "Content-Type: application/json" `
  -d '{"name":"Alex Morgan","email":"alex@example.com"}'
```

The name must not be blank. The email must be a valid email address. Email addresses are trimmed and stored in lowercase.

### Get a member and balance

```powershell
curl.exe http://localhost:8080/v1/members/1
```

Example response:

```json
{
  "member_id": 1,
  "name": "Alex Morgan",
  "email": "alex@example.com",
  "points_balance": 125,
  "created_at": "2026-10-25T10:00:00Z"
}
```

### List reward entries

```powershell
curl.exe http://localhost:8080/v1/members/1/rewards
```

Returns reward entries ordered by event date and reward ID. If the member has no entries, the response is an empty JSON array.

### Create a reward entry

```powershell
curl.exe -X POST http://localhost:8080/v1/rewards `
  -H "Content-Type: application/json" `
  -d '{"member_id":1,"point_type_id":1,"points":100,"description":"Purchase points"}'
```

`points` must be a positive integer. The service applies the sign according to the point type:

| `point_type_id` | Type | Effect |
| ---: | --- | --- |
| `1` | Purchase earning | Adds points |
| `2` | Referral bonus | Adds points |
| `3` | Cashback | Adds points |
| `4` | Redemption | Deducts points |

For example, a redemption request uses a positive `points` value; the service stores it as a negative reward entry. A redemption is rejected if the member's balance is insufficient or another redemption currently holds the member lock.

## Responses and errors

Successful creates return `201 Created`. Successful reads return `200 OK`. Errors use a JSON body of the form:

```json
{"error":"member not found"}
```

Common error statuses:

| Status | Meaning |
| ---: | --- |
| `400` | Invalid JSON, member ID, point type, points, or other input |
| `404` | Member does not exist |
| `409` | Concurrent redemption lock conflict |
| `500` | Database or other internal error |

The current error handler maps insufficient-balance redemption errors to `500 Internal Server Error`.

## Request logging and correlation

Every incoming request receives a generated request ID. The service:

- returns it in the `X-Request-ID` response header;
- stores it in the request context for downstream processing;
- includes it as the `request_id` field in request-scoped zerolog events.

Logs are JSON and include timestamps and caller information. Successful operations are logged at `Info`, invalid or expected rejections at `Warn`, and unexpected failures at `Error`.
